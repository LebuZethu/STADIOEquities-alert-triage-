# Feature Engineering

This document describes the feature engineering stage for the STADIOEquities
fraud detection and AML alert triage project.

## Related file

- **Notebook:** `notebooks/02_feature_engineering.ipynb`

## How to run

1. Ensure the project dependencies are installed (`pip install -r requirements.txt`).
2. Make sure `creditcard.csv` is in the `data/` folder.
3. Open `notebooks/02_feature_engineering.ipynb` and run the cells in order from
   top to bottom.
4. The notebook writes its output to `data/processed_fe/` (four CSV files). These
   files are excluded from version control via `.gitignore` because of their
   size, and are regenerated by running the notebook.

## An important constraint

Feature engineering means creating new, more informative input columns from the
existing data. This dataset places a real limit on what is possible. The
features V1 to V28 are anonymised principal components produced by a PCA
transformation applied for confidentiality. Because their real meaning is
hidden, it is not possible to engineer meaningful domain-based features from
them (for example, combining a location feature with a time-since-last-purchase
feature), since it is unknown which component represents what.

The only two human-readable columns are Time and Amount. All feature
engineering in this project is therefore derived from these two columns.
Acknowledging this limit, and engineering only what the data genuinely
supports, is a deliberate choice rather than an oversight.

## Features created

### 1. Hour of day (Hour)
The Time column records the seconds elapsed since the first transaction, across
a two-day period. This is converted into an hour-of-day value between 0 and 23
by dividing the seconds by 3600 to get hours, then taking the remainder after
dividing by 24 to wrap the value onto a 24-hour clock. Fraudulent activity often
occures frequently at unusual hours, late at night, so an explicit hour-of-day
feature gives the models a cleaner signal than the raw seconds value.

### 2. Log-transformed amount (Log_Amount)
Transaction amounts are unevenly distributed. Most transactions are small, but a few are very large. This imbalance can make it harder for a model to learn. A log
transform is applied using log1p (the natural log of one plus the amount), which
compresses the large values and spreads out the small ones. log1p is used rather
than a plain log so that an amount of zero does not cause an error.

## Preprocessing applied after feature engineering

After the two features are created, the notebook applies the same preprocessing
approach used in the preprocessing notebook, so that the feature-engineered data
is ready for modelling:

- The original Time column is dropped, since Hour replaces it.
- The Amount, Log_Amount, and Hour columns are standardised with StandardScaler
  so they sit on a comparable scale to V1 to V28.
- The data is split into an 80 percent training set and a 20 percent test set,
  stratified on the target with a fixed random seed.
- SMOTE is applied to the training set only, to balance the classes, while the
  test set keeps its real fraud rate.

The results are saved to `data/processed_fe/` so the modelling notebooks can
train on the feature-engineered version of the data.
